# 08 · 集合运算

> 本课目标：UNION/UNION ALL/INTERSECT/EXCEPT 的语义、去重代价、排序规则。内容不长，但它是"多来源数据合并"和 PG 里模拟 FULL JOIN 的基础。

---

## 1. 三个集合运算符

把两个"形状相同"的结果集当集合运算：

```sql
-- UNION：并集（去重）
-- UNION ALL：并集（不去重）
-- INTERSECT：交集
-- EXCEPT：差集（PG）/ EXCEPT / MINUS（Oracle）
```

**形状相同 = 列数相同 + 对应列类型兼容**。列名以第一个查询为准。

```sql
-- 谁既是买家又是评价人？（交集）
SELECT user_id FROM orders
INTERSECT
SELECT user_id FROM reviews;

-- 下过单但从没写过评价的用户（差集）
SELECT user_id FROM orders
EXCEPT
SELECT user_id FROM reviews;

-- 合并"商品名"与"分类名"两个来源的词表（并集去重）
SELECT name FROM products
UNION
SELECT name FROM categories;
```

## 2. UNION vs UNION ALL：一字之差，天壤之别

```sql
-- UNION：隐式 DISTINCT → 排序/哈希去重 → 大表上非常贵
SELECT user_id FROM orders
UNION
SELECT user_id FROM reviews;

-- UNION ALL：直接拼接，零额外代价
SELECT user_id FROM orders
UNION ALL
SELECT user_id FROM reviews;
```

| | UNION | UNION ALL |
|---|---|---|
| 去重 | ✅ | ❌（重复保留）|
| 代价 | 需要排序/哈希 | 几乎免费 |
| 顺序 | 无保证 | 无保证（但通常"前面块+后面块"）|

**经验法则：确定无重复（或业务允许重复）就用 UNION ALL**。典型如"分表合并"（orders_2024、orders_2025 各自主键不重叠）——用 UNION 纯属浪费。

### UNION ALL + 常量列：给数据打标签

```sql
-- 一个接口返回"用户时间线"：订单和评价混排
SELECT user_id, created_at, 'order' AS kind, CAST(id AS TEXT) AS ref_id
FROM orders
UNION ALL
SELECT user_id, created_at, 'review', CAST(product_id AS TEXT)
FROM reviews
ORDER BY user_id, created_at;
```

注意 `CAST(id AS TEXT)`：两侧同列类型必须兼容（id 是 INTEGER、想拼字符串就得两边都 cast）。这种"打标签 + 混排"是 feed 流、审计日志查询的标准姿势。

## 3. 优先级与括号

集合运算从上到下依次执行，**混用时必须加括号**：

```sql
-- 语义歧义示例：先 A∪B 再 ∩C？还是先 B∩C 再 ∪A？各数据库规则不一
(SELECT user_id FROM orders
 EXCEPT
 SELECT user_id FROM reviews)
UNION
SELECT user_id FROM products;   -- products.user_id 不存在，仅示意结构
```

另外，**只允许在最后一个查询末尾 ORDER BY**（对整个结果排序）；想给单块排序就包进派生表。

```sql
SELECT ... UNION ALL SELECT ... ORDER BY x;        -- ✅ 对整体排序
SELECT ... ORDER BY x UNION SELECT ...;            -- ❌ 语法错误
```

## 4. 用 UNION 模拟 FULL JOIN（MySQL）

MySQL 不支持 FULL JOIN，用两个 LEFT JOIN + UNION ALL 拼：

```sql
SELECT u.id, u.username, r.id AS review_id
FROM users u LEFT JOIN reviews r ON r.user_id = u.id
UNION ALL
SELECT u.id, u.username, r.id
FROM reviews r LEFT JOIN users u ON u.id = r.user_id
WHERE u.id IS NULL;      -- 第二块只补"右表独有"的行，UNION ALL 避免二次去重
```

这个"UNION ALL + 第二块 WHERE IS NULL"模式是去重版 UNION 的省 CPU 替代（自己保证不重，就不用数据库去重）。

## 5. EXCEPT 的语义细节

```sql
-- 左有右无：行必须在左结果中出现且不在右结果中出现
SELECT name FROM products
EXCEPT
SELECT p.name FROM products p JOIN order_items oi ON oi.product_id = p.id;
-- 从未上架卖出的商品名

-- ⚠️ EXCEPT 按整行比较（含所有列），NULL = NULL 在这里被视为相等（和 WHERE 里的 = 不同！）
SELECT NULL AS x EXCEPT SELECT NULL;   -- 0 行：两行"相等"，被去掉
```

07 课的 NOT EXISTS 也能干同样的事。区别：EXCEPT 比较整行且去重；NOT EXISTS 保留左表所有行（含重复）。要"保留重复"的差集就得 NOT EXISTS。

## 6. 常见坑

| 坑 | 说明 |
|---|---|
| 该用 UNION ALL 用了 UNION | 白付去重成本 |
| 两边列数/类型不齐 | 语法或隐式转换错误；用 CAST 对齐 |
| 忘了 UNION 去重 | "数据莫名少了"——其实是重复行被合并。检验：换 UNION ALL 看行数 |
| 中间块 ORDER BY | 语法错误；排序只写最后 |
| 用 EXCEPT 想保留重复 | EXCEPT 隐式去重，换 NOT EXISTS |

## 7. Rust 视角

集合运算结果的映射与普通查询无异，两件事值得知道：

1. **`UNION ALL` 是分页数据的多源合并利器**，配合 02 课的 keyset 分页：`... UNION ALL ... ORDER BY created_at, id LIMIT 20` 一次查询取完 feed 流；
2. sqlx `query!` 校验的是最外层结果列——两个分支列名不同时要**显式起一致别名**（`SELECT x AS kind` / `SELECT y AS kind`），否则宏报"column not found"。

```rust
#[derive(sqlx::FromRow)]
struct TimelineItem {
    user_id: i64,
    created_at: String,
    kind: String,        // 'order' | 'review'
    ref_id: String,
}
```

## 练习

1. 分别用 UNION 和 UNION ALL 合并 orders 与 reviews 的 user_id，对比行数（20+21=41；去重后 8）。
2. 找出**只出现在 reviews、不出现在 orders** 的 user_id（EXCEPT 一条）。
3. 时间线：alice（user_id=1）的所有订单与评价，混排显示 created_at、kind、金额或评分（UNION ALL + ORDER BY DESC，前 8 条）。金额列和评分列类型要兼容——都用 INTEGER 即可，各自只在相关行有值。
4. 思考题：`SELECT id, name FROM products UNION SELECT id, name FROM categories` 结果几行？这样写对吗？

<details><summary>答案</summary>

```sql
-- 1.
SELECT user_id FROM orders UNION SELECT user_id FROM reviews;        -- 8
SELECT user_id FROM orders UNION ALL SELECT user_id FROM reviews;    -- 41

-- 2.
SELECT user_id FROM reviews
EXCEPT
SELECT user_id FROM orders;

-- 3.
SELECT created_at, 'order' AS kind, total_cents AS amount_or_rating, NULL AS extra
FROM orders WHERE user_id = 1
UNION ALL
SELECT created_at, 'review', rating, comment
FROM reviews WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 8;
-- 注：amount_or_rating 列 INTEGER，extra 列 TEXT，两分支对齐

-- 4. 24+6=30 行（若 id 无重复）。语法没错但语义糟糕：两类实体被无意义混在一起，
--    id 还互相冲突（product 1 和 category 1 混淆）。集合运算要求"语义同构"，
--    不是"能跑就行"。
```
</details>
