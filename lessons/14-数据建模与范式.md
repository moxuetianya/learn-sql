# 14 · 数据建模与范式

> 本课目标：学会从需求推导表结构，掌握 1NF~3NF 与实用的反范式手法。建模决定了系统的天花板——SQL 写得再好也救不了烂模型。

---

## 1. 建模流程：需求 → 实体 → 关系 → 表

以 shop 库为例，四步法：

```
① 提取名词（实体）：   用户、商品、分类、订单、订单明细、评价
② 提取关系（动词）：
     用户 ——下——▶ 订单        （1:N）
     订单 ——包含——▶ 商品      （M:N，通过 order_items 化解）
     分类 ——归类——▶ 商品      （1:N）
     用户 ——评价——▶ 商品      （M:N，通过 reviews 化解，带属性：评分/评论）
③ 每个实体找属性：     用户(用户名, 邮箱, 角色, 注册时间)...
④ 加键与约束：         主键、外键、唯一、CHECK（10 课 checklist）
```

### 关系的三种基数怎么落表

| 关系 | 建模 |
|------|------|
| 1:1 | 任一侧加 UNIQUE 外键（如 users ↔ user_profiles）|
| 1:N | "多"侧加外键（products.category_id）|
| M:N | **连接表**（order_items：order_id + product_id + 关系属性 quantity/unit_price）|

> 连接表不只是两个外键——**关系的属性**（买了几件、成交单价）放连接表，实体的属性放实体表。这是新手最常犯的建模错误：把"订单的价格"塞进 products（商品价格会变，订单记录的是成交时刻价）。

## 2. 范式：为什么拆表

反例（一张"万能表"）：

```
order_table: 订单号 | 用户名 | 用户邮箱 | 商品1名 | 商品1价 | 商品2名 | 商品2价 | 总额
```

灾难现场：

- 用户改邮箱 → 每笔历史订单都要改（**修改异常**）；
- 新用户没下过单 → 没地方存（**插入异常**）；
- 只有一条订单的用户删单 → 用户信息也消失了（**删除异常**）；
- 商品 3 件怎么办？加列？（**不可扩展**）。

范式就是拆表规则，逐级消除这些异常。

### 1NF：原子性

每个单元格只存**一个**值，禁止重复组/逗号分隔列表：

```
❌ products: id | name | tags(='键盘,机械,87键')
✅ products: id | name
   tags:     product_id | tag          -- 拆表；PG 里也可用原子数组/JSONB（后述权衡）
```

### 2NF：消除部分依赖（针对联合主键）

非键列必须依赖**完整主键**，不能只依赖一部分：

```
❌ order_items: (order_id, product_id) 为主键，但表里还有 product_name
   → product_name 只依赖 product_id（半个主键）→ 商品改名要改所有历史明细
✅ product_name 放 products 表，order_items 只留 quantity / unit_price_cents
```

### 3NF：消除传递依赖

非键列不能依赖另一个非键列：

```
❌ orders: id | user_id | username | user_level
   → username 依赖 user_id 依赖 id（传递）→ 用户改名要刷全表订单
✅ orders 只留 user_id，username 回 users 表
```

口诀：**"键、整个键、除了键什么都不依赖"（the key, the whole key, and nothing but the key）**。

### 反范式：明知故犯的冗余

3NF 是**默认起点**，不是终点。为了读性能可以有意冗余，前提：冗余数据**不会漂移**或**漂移无所谓**：

| 反范式手法 | 场景 |
|-----------|------|
| `orders.total_cents` 冗余合计 | 明细变了要同步更新；但报表/列表页高频读，省一次 join 聚合，值 |
| 地址快照：`orders.ship_addr` 复制下单时刻地址 | 用户改地址不影响历史订单——快照语义，本来就该冗余 |
| 计数器：`products.sales_cnt` | 高频读，低频事务内维护（`UPDATE ... SET sales_cnt=sales_cnt+1`）|
| 汇总表：`daily_revenue(date, amount)` | 定时/物化刷新，报表直读 |

**判据：读的收益 > 写的一致性成本，且更新路径收敛在少数事务里。** 无脑冗余 = 回到更新异常地狱。

## 3. 常用建模模式（后端高频）

### 枚举：CHECK / 独立表 / PG ENUM

```sql
-- 方案1: CHECK 白名单（shop 库方案，简单直观，改值需 DDL）
status TEXT CHECK (status IN ('pending','paid',...))

-- 方案2: 枚举表（可扩展、可加属性：sort_order、display_name）
CREATE TABLE order_statuses (code TEXT PRIMARY KEY, label TEXT NOT NULL);

-- 方案3: PG 原生枚举
CREATE TYPE order_status AS ENUM ('pending','paid','shipped','completed','cancelled');
-- 16 课: sqlx 直接映射 Rust enum
```

### 多态关联 ❌ → 显式关联 ✅

```
❌ comments: id | target_type('product'|'order') | target_id
   → 外键无法建立，数据库管不了完整性
✅ comments: id | product_id NULL REFERENCES products(id),
                 order_id  NULL REFERENCES orders(id)   -- 各自可空外键 + CHECK 恰好一个非空
```

### 层级结构：邻接表 + 递归 CTE

```sql
CREATE TABLE categories_tree (
    id        INTEGER PRIMARY KEY,
    name      TEXT NOT NULL,
    parent_id INTEGER REFERENCES categories_tree(id)   -- 邻接表：每行记父节点
);
-- 查子树用 07 课的 WITH RECURSIVE；频繁读整棵树可考虑物化路径(path '1/4/9/')或闭包表
```

### 审计与时间

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),   -- PG: 触发器维护；应用层: 每次UPDATE带上
deleted_at TIMESTAMPTZ                           -- 软删除（11 课）
```

### 金额与精度（回顾 01/04 课）

```
✅ price_cents BIGINT 或 NUMERIC(12,2)
❌ price FLOAT/DOUBLE —— 0.1+0.2≠0.3，对账日你会上新闻
Rust 侧: i64 / rust_decimal::Decimal，永远别 f64 存钱
```

## 4. shop 库建模复盘

用上面的标准复盘示例库的每个决策：

| 决策 | 依据 |
|------|------|
| order_items 用联合主键 (order_id, product_id) | 同单同商品只一行，天然幂等；数量用 quantity 累加 |
| order_items 存 unit_price_cents 快照 | 成交价不随商品调价漂移（快照语义）|
| orders.total_cents 冗余 | 列表页高频读；由下单事务统一写入 |
| reviews UNIQUE(user_id, product_id) | 业务规则"一人一评"下沉为约束 |
| users.role 用 CHECK | 枚举值稳定、集合小 |
| 所有主键代理 id | natural key（username）会改、有隐私问题 |
| categories 独立成表而非 products 上加 TEXT 列 | 1NF + 分类自身要挂属性（图标、排序）|

## 5. 实战：从需求到模型

需求：**博客系统**——用户写文章（可草稿/发布），文章有多个标签，读者可评论（支持楼中楼），作者可收藏文章。

```
① 实体：users, posts, tags, comments
② 关系：
   users 1—N posts          （author）
   posts M—N tags           （post_tags 连接表）
   users 1—N comments       （commenter）
   posts 1—N comments       （文章下的评论）
   comments 1—N comments    （自引用：楼中楼 parent_id）
   users M—N posts 收藏      （favorites 连接表 + created_at 属性）
③ 属性：posts(title, slug UNIQUE, content, status, published_at, view_cnt...)
④ 约束：slug 唯一；status CHECK；parent_id 自引用外键；favorites 复合主键
```

```sql
CREATE TABLE posts (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    author_id    BIGINT NOT NULL REFERENCES users(id),
    title        TEXT NOT NULL,
    slug         TEXT NOT NULL UNIQUE,
    content      TEXT NOT NULL,
    status       TEXT NOT NULL DEFAULT 'draft' CHECK (status IN ('draft','published')),
    view_cnt     BIGINT NOT NULL DEFAULT 0,        -- 反范式计数器
    published_at TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_pub CHECK (status = 'draft' OR published_at IS NOT NULL)
);
CREATE TABLE post_tags (
    post_id BIGINT NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
    tag_id  BIGINT NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    PRIMARY KEY (post_id, tag_id)
);
```

## 6. 常见坑

| 坑 | 说明 |
|---|---|
| M:N 不建连接表 | 出现重复列/逗号列表（违反 1NF） |
| 关系属性放错表 | 成交价放商品表、评论时间放用户表 |
| 过度反范式 | 一上来就冗余，没有读压力证明；先 3NF 再按数据说话 |
| 教条范式化 | 报表场景 6 表 join 也不合理——物化视图/汇总表是正解 |
| 忽略时间维度 | 历史快照（价格、地址、状态）是电商核心需求，建模时就要想清楚 |
| 用字符串存枚举还不加 CHECK | 脏值 silently 入库，Rust enum 反序列化时爆炸 |
| 主键用 UUIDv4 随机值当聚簇键 | PG 堆表无碍；MySQL InnoDB 插入随机导致页分裂（用自增+唯一UUID列 或 UUIDv7） |

## 7. Rust 视角

模型 ↔ 类型系统一一对应，是 Rust 后端的天然优势：

```rust
// 枚举约束 → Rust enum + sqlx 映射（16 课）
#[derive(sqlx::Type)]
#[sqlx(type_name = "text", rename_all = "lowercase")]
enum OrderStatus { Pending, Paid, Shipped, Completed, Cancelled }

// M:N 连接表 → 不建 struct，只在 SQL 里 JOIN；
// 领域对象只表达实体: struct Post { ... tags: Vec<Tag> }  ← 由查询组装（一次 join + json_agg 或两查 + HashMap）

// 快照语义 → 用 newtype 区分: struct UnitPriceCents(i64); 防止与 PriceCents 混用
```

DDD 视角：表结构是"持久化模型"，不必与领域模型 1:1——领域层 `Order` 聚合含 items，但存储仍是两张表 + 事务组装。
