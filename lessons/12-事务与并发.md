# 12 · 事务与并发

> 本课目标：理解 ACID、隔离级别与并发异常，能安全地使用 BEGIN/COMMIT/ROLLBACK、SELECT ... FOR UPDATE、乐观锁。事务正确性直接决定资金/库存类业务是否成立。

---

## 1. 事务：要么全成，要么全不算

```sql
BEGIN;                                        -- 或 BEGIN TRANSACTION / START TRANSACTION (MySQL)
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                                       -- 确认 → 两条同时生效
-- ROLLBACK;                                  -- 反悔 → 两条一起消失
```

**ACID**：

| 字母 | 含义 | 谁负责 |
|------|------|--------|
| **A**tomicity 原子性 | 全做或全不做 | 事务日志（undo）|
| **C**onsistency 一致性 | 约束不被破坏 | 约束 + 应用逻辑 |
| **I**solation 隔离性 | 并发事务互不干扰（程度看隔离级别）| MVCC / 锁 |
| **D**urability 持久性 | COMMIT 后断电也不丢 | WAL + fsync |

**什么时候需要事务？多写操作且必须同生共死时**。单条 SQL 自带原子性；两条 UPDATE 之间没有事务包裹，进程崩溃就出现"扣了款没发货"。

### 经典案例：下单三步走

```sql
BEGIN;
-- ① 扣库存（条件更新防超卖）
UPDATE products SET stock = stock - 2 WHERE id = 1 AND stock >= 2;
-- ② 建订单
INSERT INTO orders (user_id, status, total_cents) VALUES (1, 'paid', 379800)
RETURNING id;                              -- 假设 21
-- ③ 写明细
INSERT INTO order_items (order_id, product_id, quantity, unit_price_cents)
VALUES (21, 1, 2, 189900);
COMMIT;
```

任何一步失败 → ROLLBACK，库存、订单、明细全部回滚，不留半成品。

> SQLite 特性：整个数据库同一时刻只有一个写事务（写锁串行），并发异常天然不存在，代价是写吞吐低。**并发语义请以 PostgreSQL/MySQL 为准来学**，它们才是生产主力。

## 2. 并发异常四兄弟（理解隔离级别的钥匙）

两个事务 T1/T2 同时跑，可能撞出：

| 异常 | 场景 |
|------|------|
| **脏读** | T1 读到 T2 **未提交**的数据，T2 一回滚，T1 拿着幻影值做了决策 |
| **不可重复读** | T1 两次读**同一行**结果不同（T2 中途改了它并提交）|
| **幻读** | T1 两次按同条件查询，**行数**变了（T2 插入/删除了匹配行）|
| **丢失更新** | T1、T2 都读-改-写同一行，后写的覆盖先写的（余额越扣越多/越减越多）|

## 3. 隔离级别对照表

| 级别（标准） | 脏读 | 不可重复读 | 幻读 | 备注 |
|--------------|------|-----------|------|------|
| READ UNCOMMITTED | 😱可能 | 可能 | 可能 | 几乎没人用 |
| READ COMMITTED（PG 默认）| 安全 | 可能 | 可能 | 语句级快照 |
| REPEATABLE READ（MySQL 默认）| 安全 | 安全 | 可能* | 事务级快照 |
| SERIALIZABLE | 安全 | 安全 | 安全 | 最严，性能最差 |

\* MySQL 的 RR 通过间隙锁基本杜绝幻读；PG 的 RR 是快照隔离，会有**写倾斜（write skew）**，真正串行化要 SERIALIZABLE（SSI）。

```sql
-- 设置隔离级别（PG，事务开始前/中）
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- MySQL: SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

**后端经验**：PG 默认 READ COMMITTED 够用 95% 场景；涉及"读后写"的临界区（余额、库存、配额）用下面两节的原生手段（悲观/乐观锁）解决，别盲目升级全局隔离级别。

## 4. 悲观锁：SELECT ... FOR UPDATE

"我要改这行，别人都别动"：

```sql
BEGIN;
SELECT * FROM orders WHERE id = 7 FOR UPDATE;   -- 锁住这行（其他事务的 FOR UPDATE 会等待）
UPDATE orders SET status = 'shipped' WHERE id = 7;
COMMIT;                                         -- 释放锁
```

变体：

| 语法 | 语义 |
|------|------|
| `FOR UPDATE` | 锁行，禁止他人读锁/写 |
| `FOR NO KEY UPDATE` | 锁行但允许他人插外键引用（PG 细分）|
| `FOR SHARE` | 共享锁：大家能读，都不能写 |
| `SKIP LOCKED` | 锁不上就**跳过**——任务队列神器 |
| `NOWAIT` | 锁不上立刻报错（不等待）|

### 任务队列模式（SKIP LOCKED，后端高频）

```sql
-- 多个 worker 并发抢单，互不冲突、互不等待：
WITH next_job AS (
    SELECT id FROM jobs
    WHERE status = 'pending'
    ORDER BY created_at
    LIMIT 1
    FOR UPDATE SKIP LOCKED               -- 被别的 worker 锁住的行直接跳过
)
UPDATE jobs SET status = 'running', worker = 'w1'
WHERE id IN (SELECT id FROM next_job)
RETURNING id, payload;
```

## 5. 乐观锁：版本号/条件更新

不加锁，更新时校验"数据还是我读出来时那样吗"：

```sql
-- 方案A：版本号列
UPDATE docs SET content = 'new', version = version + 1
WHERE id = 42 AND version = 5;            -- 版本不匹配 → 0 行 → 重读重试
RETURNING version;

-- 方案B：状态条件（有限状态机天然自带）
UPDATE orders SET status = 'shipped' WHERE id = 7 AND status = 'paid';
-- affected_rows = 0 说明已被并发流转，业务层处理冲突
```

**选型**：

- 冲突**少**（编辑文档、用户资料）→ 乐观锁，无锁开销，冲突时重试；
- 冲突**多**（秒杀库存、账户余额）→ 悲观锁（或直接 `UPDATE ... SET stock=stock-1 WHERE stock>=n` 原子条件更新，本质是数据库内建的原子性）。

## 6. 死锁

T1 锁 A 等 B，T2 锁 B 等 A → 互相等待到永远。数据库会检测并**牺牲一个事务**（回滚它，报 `deadlock detected`）。

```sql
-- 死锁现场复现（两个会话，pg/sqlite 均示意）：
-- 会话1: BEGIN; UPDATE products SET stock=stock-1 WHERE id=1;
-- 会话2: BEGIN; UPDATE products SET stock=stock-1 WHERE id=2;
-- 会话1: UPDATE products SET stock=stock-1 WHERE id=2;  -- 等会话2
-- 会话2: UPDATE products SET stock=stock-1 WHERE id=1;  -- 等会话1 → 死锁!
```

预防三板斧：

1. **多行更新按固定顺序**（如按 id 升序）；
2. **事务短小**：事务里别调外部 HTTP、别等用户输入；
3. 捕获死锁错误（PG `40P01`）→ **重试**整个事务（sqlx 17 课给出重试封装）。

## 7. 工程规范（团队 code review 检查项）

- [ ] 事务里只做 DB 操作，**无 RPC/IO/重计算**；
- [ ] 事务粒度最小化：能拆成两个独立事务就拆（长事务 = 锁持有久 + 主从延迟大）；
- [ ] 多行写按统一顺序访问；
- [ ] 乐观冲突与死锁要有重试策略（带退避与次数上限）；
- [ ] 失败路径确保 ROLLBACK（或用框架的"事务闭包"自动回滚）。

## 8. Rust 视角（sqlx 事务闭包）

```rust
use sqlx::sqlite::SqlitePool;

async fn place_order(pool: &SqlitePool, uid: i64, pid: i64, qty: i64) -> anyhow::Result<i64> {
    let mut tx = pool.begin().await?;                       // BEGIN

    let (price,): (i64,) = sqlx::query_as(
        "SELECT price_cents FROM products WHERE id = ?1")
        .bind(pid).fetch_one(&mut *tx).await?;

    let res = sqlx::query(
        "UPDATE products SET stock = stock - ?1 WHERE id = ?2 AND stock >= ?1")
        .bind(qty).bind(pid).execute(&mut *tx).await?;
    anyhow::ensure!(res.rows_affected() == 1, "库存不足");

    let (order_id,): (i64,) = sqlx::query_as(
        "INSERT INTO orders (user_id, status, total_cents) VALUES (?1,'paid',?2)
         RETURNING id")
        .bind(uid).bind(price * qty).fetch_one(&mut *tx).await?;

    sqlx::query(
        "INSERT INTO order_items (order_id, product_id, quantity, unit_price_cents)
         VALUES (?1, ?2, ?3, ?4)")
        .bind(order_id).bind(pid).bind(qty).bind(price).execute(&mut *tx).await?;

    tx.commit().await?;                                     // COMMIT；任意 ? 提前返回 → 连接回池自动 ROLLBACK
    Ok(order_id)
}
```

两个关键点：

1. `&mut *tx`：事务是排他的，借用检查器在**编译期**阻止你并发使用同一事务；
2. `tx` 不 commit 就 drop → sqlx 自动回滚，`?` 传播错误的路径天然安全。

PG 侧 `sqlx::query("... FOR UPDATE")` 语法完全一致；重试封装（死锁/序列化冲突）见 17 课。

## 练习

（练习 1~3 在 sqlite3 单连接里用两个终端模拟并发并不真实——若装了 PG 强烈建议用两个 `psql` 会话做；SQLite 下做语义验证即可）

1. 开事务 → 删除 reviews 表一行 → 在**未 COMMIT** 前 `SELECT COUNT(*)`（看到少了一行）→ `ROLLBACK` → 再数（回来了）。体会原子性。
2. 把第 11 课练习 3 的"下单三步"改写成显式事务，并在第 ② 步故意写错列名，验证 ① 的库存扣减也被回滚。
3. 用条件更新实现"每个用户最多 5 张未用券"：`UPDATE ... WHERE (SELECT COUNT(*) FROM coupons WHERE user_id=? AND status='unused') < 5` 有什么并发问题？（提示：READ COMMITTED 下两个事务同时数到 4）正确做法是什么？
4. 文档编辑场景选乐观锁：给 docs 表加 version 列，写出"读 v3 → 提交时校验版本"的两条 SQL，并说明 0 行受影响时客户端该干什么。
5. 任务队列：jobs 表（id, status, payload），写出用 `FOR UPDATE SKIP LOCKED` 领任务的完整 SQL（PG）。

<details><summary>答案</summary>

```sql
-- 1.
BEGIN;
DELETE FROM reviews WHERE id = 1;
SELECT COUNT(*) FROM reviews;   -- 20
ROLLBACK;
SELECT COUNT(*) FROM reviews;   -- 21 恢复

-- 2.
BEGIN;
UPDATE products SET stock = stock - 2 WHERE id = 1 AND stock >= 2;
INSERT INTO orders (user_id, status, total_cents) VALUES (1, 'paid', 0);  -- 先占位
INSERT INTO order_itemsss (order_id, product_id, quantity, unit_price_cents)   -- 故意拼错表名 → 报错
VALUES (last_insert_rowid(), 1, 2, 189900);
COMMIT;    -- 不会执行到这，整个事务回滚 → 验证 stock 没变

-- 3. 问题：两个并发事务都执行子查询 COUNT=4 → 都通过 → 插入第 6 张。
--    正确做法（PG）：
BEGIN;
SELECT COUNT(*) FROM coupons
  WHERE user_id = 1 AND status = 'unused' FOR UPDATE;   -- 锁住该用户的券行，串行化临界区
-- 或者：为用户建"配额行" quotas(user_id, used) 并原子更新：
UPDATE quotas SET used = used + 1 WHERE user_id = 1 AND used < 5;  -- 0 行 = 超额

-- 4.
SELECT id, content, version FROM docs WHERE id = 42;            -- 读到 version=3
UPDATE docs SET content = 'new content', version = version + 1
WHERE id = 42 AND version = 3
RETURNING version;                                              -- 0 行 = 冲突
-- 客户端：重新读最新版 → 合并/提示用户 → 带新版本号重试（设重试上限）。

-- 5. (PG)
WITH next AS (
    SELECT id FROM jobs WHERE status = 'pending'
    ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
)
UPDATE jobs j SET status = 'running'
FROM next WHERE j.id = next.id
RETURNING j.id, j.payload;
```
