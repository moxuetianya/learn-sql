# 13 · 索引与性能优化

> 本课目标：理解 B-tree 索引原理与最左前缀法则，会用 EXPLAIN 分析执行计划，掌握慢查询排查清单。这是 SQL 从"会写"到"写好"的一课。

---

## 1. 没有索引的世界：全表扫描

```sql
-- 查 alice 的订单
SELECT * FROM orders WHERE user_id = 1;
```

无索引时数据库只能**从头到尾扫每一行**（Seq Scan / Table Scan）。20 行无所谓，2000 万行就是 2000 万次比较 + 磁盘 IO——这就是"接口 P99 突然 3 秒"的头号原因。

## 2. B-tree 索引：一本按序装订的字典

```
                [ 15 ]
              /        \
        [ 7 ]            [ 23 ]
       /     \          /      \
   [3,5]  [9,11]   [17,19]   [25,27]
```

- 按 key 有序存放 → **等值查找 O(log n)**（2000 万行 ≈ 4 次页访问）；
- 有序 → 天然支持**范围查询**（BETWEEN、>、<）与 **ORDER BY 免排序**；
- 叶节点带指向行的指针（rowid/TID），找到索引项后回表取整行。

```sql
-- shop 库在建表时已建：
CREATE INDEX idx_orders_user ON orders(user_id);
CREATE INDEX idx_products_category ON products(category_id);
CREATE INDEX idx_order_items_product ON order_items(product_id);
CREATE INDEX idx_reviews_product ON reviews(product_id);

-- 查看某表的索引（SQLite）
PRAGMA index_list(orders);
-- PG: \di 或 SELECT * FROM pg_indexes WHERE tablename='orders';
```

### 哪些查询能吃上索引？

| 谓词 | 走索引？ |
|------|---------|
| `col = 5`、`col IN (...)` | ✅ |
| `col > 5 AND col < 10`、`BETWEEN` | ✅（范围）|
| `col LIKE 'abc%'`（前缀）| ✅ |
| `col LIKE '%abc'`（后缀）| ❌（字典没法按"结尾"查）|
| `UPPER(col) = 'ABC'`（对列套函数）| ❌（除非函数索引）|
| `col1 = 1 AND col2 = 2`（有 (col1,col2) 复合索引）| ✅ |
| `col2 = 2`（仅有 (col1,col2) 索引）| ❌（最左前缀！）|

## 3. 复合索引与最左前缀法则

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
```

它相当于"先按 user_id 排、再按 status 排"的电话簿：

```
(user_id=1, status=paid)
(user_id=1, status=completed)
(user_id=1, status=completed)     ← user_id 确定后 status 内部有序
(user_id=2, status=cancelled)
...
```

- ✅ `WHERE user_id=1` —— 用索引前半段；
- ✅ `WHERE user_id=1 AND status='paid'` —— 全用；
- ❌ `WHERE status='paid'` —— 电话簿没法按"名"查（除非再建 `(status)` 索引）；
- ⚠️ `WHERE user_id>1 AND status='paid'` —— user_id 用范围后，status 部分"失序"，过滤效率降级。

**设计口诀：等值列在前，范围列在后；高频查询驱动索引设计。**

## 4. 覆盖索引：连回表都省了

```sql
-- 只要 id 和 stock，而索引里就有：
CREATE INDEX idx_products_stock ON products(stock);

SELECT id, stock FROM products WHERE stock < 10;
-- 索引 leaf = (stock, rowid=id) → 查询所需列全在索引里 → Index Only Scan，0 次回表
```

这就是 02 课"别写 SELECT *"的深层原因：**查的列越少，越有机会整条查询只碰索引**。PG 里 `EXPLAIN` 显示 `Index Only Scan`，SQLite 显示 `SEARCH ... USING COVERING INDEX`。

## 5. EXPLAIN：看数据库怎么执行

```sql
-- SQLite：EXPLAIN QUERY PLAN（人类可读版）
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE user_id = 1;
-- ✅ SEARCH orders USING INDEX idx_orders_user (user_id=?)

EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE total_cents > 300000;
-- ❌ SCAN orders（全表扫：total_cents 没索引）

EXPLAIN QUERY PLAN
SELECT id, user_id FROM orders WHERE user_id = 1;
-- ✅ SEARCH ... USING COVERING INDEX idx_orders_user

-- PG：EXPLAIN ANALYZE 真实执行并显示耗时/行数
EXPLAIN ANALYZE
SELECT o.id, u.username FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.user_id = 1;
```

PG 输出关键行（学会读这四样就够入门）：

```
Nested Loop Left Join  (...)  (cost=0.29..16.35 rows=3 width=...) (actual time=0.02..0.05 rows=3 loops=1)
  -> Index Scan using idx_orders_user on orders o  (actual rows=3 loops=1)   ← 索引扫描,好
  -> Index Scan using users_pkey on users u  (actual rows=1 loops=3)
```

1. **节点类型**：`Index Scan` ✅ / `Seq Scan`（大表）⚠️ / `Nested Loop`、`Hash Join`（连接策略）/ `Sort`（内存排序，看是否溢出）；
2. **cost/actual time**：预估 vs 真实，偏差大 = 统计信息过期（`ANALYZE 表名` 刷新）；
3. **rows**：每步实际行数——join 后爆炸通常在这里现形；
4. **loops**：嵌套循环里内侧执行次数，`rows×loops` 才是真实量。

## 6. 索引的代价与正确姿势

索引不是免费的：

- **写放大**：每次 INSERT/UPDATE 都要同步维护所有索引（索引越多写入越慢）；
- **空间**：索引通常占表 20%~100% 大小；
- ** optimizer 选择**：小表全扫可能比走索引快，优化器自己会权衡（别看到 Seq Scan 就慌）。

姿势清单：

```sql
-- 1. 建在"高选择性 + 高频查询"列：外键列几乎必建
CREATE INDEX idx_order_items_order ON order_items(order_id);   -- PK 已含 (order_id, product_id) 则可省

-- 2. 部分索引（PG）：只索引热数据，写入负担小一个量级
CREATE INDEX idx_orders_pending ON orders(created_at) WHERE status = 'pending';

-- 3. 函数索引（PG）：让"对列套函数"的查询也能走索引
CREATE INDEX idx_users_email_lower ON users(LOWER(email));
SELECT * FROM users WHERE LOWER(email) = 'alice@example.com';   -- 现在能走索引了

-- 4. 表达式/复合覆盖，按真实查询来
CREATE INDEX idx_sales ON order_items(product_id, quantity, unit_price_cents);

-- 5. 删除没用的索引（先观察使用情况）
-- PG: SELECT * FROM pg_stat_user_indexes WHERE idx_scan = 0;   -- 从未被扫过
DROP INDEX idx_orders_status;
```

## 7. 慢查询排查清单（背下来）

按顺序过一遍，90% 慢查询能定位：

1. **EXPLAIN**：是 Seq Scan 大表？Sort 溢出？join 行数爆炸？
2. **谓词分析**：WHERE 的列有索引吗？是否对索引列套函数/做了运算/前导 % LIKE？
3. **最左前缀**：复合索引顺序匹配查询吗？
4. **SELECT \***：能不能只取需要的列（覆盖索引）？
5. **JOIN 顺序与键**：join 键有索引吗？小表驱动大表了吗？
6. **分页**：深 OFFSET → keyset 分页（02 课）；
7. **统计信息**：`ANALYZE table`（PG）刷新后计划是否变化；
8. **数据量**：是不是单表太大该分区/归档了（超出索引能力）；
9. **N+1 查询**：应用层循环查库（Rust 里 `for id in ids { query(id) }`）→ 改 `WHERE id = ANY($1)` 批量；
10. **连接池耗尽**：查询不慢，是排队慢（17 课池调优）。

## 8. 实战：优化一条慢查询

```sql
-- 慢查询：每个用户的订单数 + 总额（join + group）
EXPLAIN QUERY PLAN
SELECT u.id, u.username, COUNT(o.id) cnt, COALESCE(SUM(o.total_cents),0) spent
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.username;
```

分析：

- `orders.user_id` 有 idx_orders_user ✅，join 是 indexed nested loop；
- users 全表 8 行扫一次，正常；
- 若 orders 表涨到千万行：`GROUP BY u.id` 每组聚合来自 join 流，无需额外排序——这个计划其实已经不错；
- 进一步优化思路：用户量大而**有订单**的用户少时，可先 `GROUP BY user_id` 子查询聚合，再 LEFT JOIN users（减少 join 次数：28 次 join → 8 次）。

再看反例：

```sql
-- 查 3 月的大额订单
SELECT * FROM orders
WHERE strftime('%Y-%m', created_at) = '2025-03' AND total_cents > 200000;
-- ❌ 对 created_at 套函数 → created_at 上任何索引都失效 → 全表扫描

-- ✅ 改写为范围查询（闭开区间）
SELECT * FROM orders
WHERE created_at >= '2025-03-01' AND created_at < '2025-04-01'
  AND total_cents > 200000;
-- created_at 有索引（若有 idx_orders_created_at）即可走范围扫描
```

**核心思想：让列"裸奔"参与比较，把变换搬到常量侧。**

## 9. 常见坑

| 坑 | 说明 |
|---|---|
| 索引列上运算/函数 | `WHERE col+1=2`、`WHERE func(col)=x` 索引失效；改写常量侧或建函数索引 |
| 前导 % 的 LIKE | 无法用 B-tree；用全文索引（15 课） |
| 复合索引顺序乱 | 等值在前、范围在后；顺序错了等于没建 |
| 索引冗余 | `(a)` 与 `(a,b)` 并存时 `(a)` 多余；`(a,b)` 覆盖最左场景 |
| 唯一约束重复当索引用 | UNIQUE 本身就是索引 ✅（这个不算坑，是知识点） |
| 滥用索引 | 写密集表索引一堆 → 写入雪崩。按查询建，定期清理零使用索引 |
| EXPLAIN 只看一次 | 数据分布变化后计划会变；优化要留 benchmark |

## 10. Rust 视角

- sqlx 的 `query!` 不影响执行计划，但**编译期类型推断能防止你随手 `SELECT *`**（struct 字段必须列列对齐）；
- N+1 是 Rust 后端最常见的性能问题：Axum handler 里 `for product in products { query_reviews(product.id) }` → 一条 `LEFT JOIN` 或 `WHERE product_id IN (...)` 批量查回再 `HashMap` 分组；
- PG 的 `ANY` 数组参数天然防 N+1：`.bind(vec![1,2,3])` + `WHERE id = ANY($1)`；
- 池配置（`max_connections`）与慢查询互相伪装：先 EXPLAIN 再看池（17 课）。

1. 用 `EXPLAIN QUERY PLAN` 对比 `WHERE user_id = 1`（orders）与 `WHERE total_cents > 100000`（orders）的计划差异。
2. 验证最左前缀：建 `CREATE INDEX idx_t ON products(category_id, price_cents);` 后，分别 EXPLAIN：`WHERE category_id=2`、`WHERE category_id=2 AND price_cents<100000`、`WHERE price_cents<100000`（最后一个应 SCAN；做完 DROP INDEX idx_t）。
3. 把 `WHERE SUBSTR(created_at,1,7)='2025-03'` 改写成能走索引的形式并 EXPLAIN 对比。
4. 为"查某用户的所有 pending 订单，按创建时间倒序"设计最优索引（写出 CREATE INDEX，并 EXPLAIN 验证 SEARCH + 无 SORT）。
5. 思考题：`SELECT COUNT(*) FROM order_items WHERE product_id = 1` 每次都 2ms，但接口 P99 是 800ms，列出 3 个库外可能原因。

```sql
-- 1.
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 1;          -- SEARCH USING idx_orders_user

-- 2.
CREATE INDEX idx_t ON products(category_id, price_cents);
EXPLAIN QUERY PLAN SELECT * FROM products WHERE category_id = 2;                    -- SEARCH idx_t (category_id=?)
EXPLAIN QUERY PLAN SELECT * FROM products WHERE category_id = 2 AND price_cents < 100000;  -- SEARCH idx_t (category_id=? AND price_cents<?)
EXPLAIN QUERY PLAN SELECT * FROM products WHERE price_cents < 100000;               -- SCAN products
DROP INDEX idx_t;

-- 3.
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE SUBSTR(created_at,1,7)='2025-03';       -- SCAN

DROP INDEX idx_orders_created;

EXPLAIN QUERY PLAN

ORDER BY created_at DESC;

DROP INDEX idx_orders_user_status_created;
```
